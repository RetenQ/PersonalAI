# 任务操作、自动动态与页面含义

日期：2026-10-29。本机实现，尚未提交、推送或部署。本轮不修改 APK、客户端协议或模型授权。

## 使用方式

1. 在“总览”点击新增任务，或在“日志与任务”选择任务；填写内容、计划日期，可同时关联目标。
2. 点击任务进入详情，选择“完成任务”“标为部分完成”或“恢复待进行”。状态修改只展示任务内容及前后状态，确认后保存；也可拒绝或暂留待确认。
3. 内容和计划日期的更正继续使用原有编辑及确认流程；修改既有目标归属也需要确认。
4. 在“日志与任务”查看“任务与目标动态”；每日回顾自动纳入当日已保存的变化。动态按变化发生时间归日，不按任务计划日期归日。

## 统一页面含义

| 页面 | 职责 |
|---|---|
| 概述 | 查看当天计划任务、目标进度及目标下的未完成任务 |
| 总览 | 管理目标、归属、待确认事项及快捷记录；与概述共用任务日期和状态口径 |
| 日志与任务 | 新增日常记录或任务、维护任务、查看自动动态及查询历史 |
| 每日回顾 | 当天和前一天的事实摘要、已有 AI 分析、早中晚回应 |
| 设置 | 界面、任务类型、模型、分析安排、权限、备份及服务信息 |

- 今日任务按计划日期筛选，包括当天计划中已完成的任务；不会将旧任务今天完成误认为今天才计划。
- 目标下的当前任务只包括待进行和部分完成任务；完成后仍在当天任务和历史中可查。
- `open`＝待进行，`partial`＝部分完成，`done`＝已完成。旧版“部分完成”没有重解释为“进行中”。
- 任务没有新增自身百分比；完成任务不会直接改变目标进度。未知目标进度仍然未知。
- 旧想法保留“待定任务（原想法）”标记，没有自动转为正式任务。

## 实现与接口

### 创建任务

新增网页内部 `POST /api/tasks`，复用原 `CreateRecord` 字段，固定 `kind=task`，增加可空 UUID `goal_id`。仍需本人会话、CSRF 和 tracking 插件。

任务与初始追踪信息放在同一个原子事件中，沿用请求编号幂等。不存在的目标会拒绝整个请求，不留下半条记录。返回 `{record: ...}`，旧 `/api/records` 保持兼容。后续修订仍走原有版本检查和提案确认机制。

### 自动动态

`GET /api/task-events?day=YYYY-MM-DD` 是本人可读的历史投影，按 Asia/Shanghai 筛选保存时间，倒序返回 `items`。来源包括：

- 任务创建、状态、内容、计划日期、类别的已保存变更。
- 任务初次关联目标及确认后的归属修改。
- 目标创建、完成标准、计算规则、数值及目标进度的已确认变化。

每项含稳定 `id`、`task_id`（可空）、可选 `entity_id`、`version`、`time`、`title`、`action`。名称按变更当时版本解析，后续改名不会悄悄改写旧归属动态。网页可打开对应来源历史。

读取不写入事件，不生成额外活动日志；待确认和被拒绝的修改不会变为正式动态。日报摘要引用这些变化，创建目标和任务只描述为创建，不当作执行完成。

本轮自动动态是确定性整理，没有新增 AI 调用。现有目标分析、定时分析与授权保留；不能宣称现有模型已自动分析这份新增动态投影。若后续让模型直接引用动态，需要单独扩展来源版本及发送预览。
